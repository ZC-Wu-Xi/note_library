## 一. Git 中的 `pull`、`fetch` 和 `rebase` 

Git 中的 `pull`、`fetch` 和 `rebase` 都是用于同步远程仓库和本地仓库的命令，但它们的用途和工作方式有所不同。以下是它们的区别：

------

### 1. **`git fetch`**

- **作用**：从远程仓库下载最新的提交（commit）、分支（branch）和标签（tag）信息，但**不会自动合并或修改本地代码**。
- **特点**：
  - 只获取远程的更新，不会影响本地的工作目录（working directory）或当前分支。
  - 你需要手动合并（`git merge`）或变基（`git rebase`）来应用这些更新。
- **使用场景**：
  - 查看远程仓库的最新状态，但不立即合并到本地。
  - 安全地检查远程变更后再决定是否合并。

**示例**：

```shell
git fetch origin  # 获取远程仓库 origin 的所有更新
git log origin/main  # 查看远程 main 分支的更新（但本地 main 分支未变）
```

------

### 2. **`git pull`**

- **作用**：`git fetch` + `git merge` 的组合操作。它会从远程仓库下载最新内容并**自动合并到当前分支**。
- **特点**：
  - 默认行为是 `fetch` + `merge`（如果当前分支跟踪了远程分支）。
  - 可以通过参数改为 `fetch` + `rebase`（`git pull --rebase`）。
- **使用场景**：
  - 快速拉取远程变更并直接合并到本地（适合简单的协作场景）。
  - 如果本地没有未提交的更改，直接使用 `pull` 可以简化流程。

**示例**：

```shell
git pull origin main  # 拉取远程 main 分支并合并到当前分支
git pull --rebase origin main  # 拉取远程 main 分支并以 rebase 方式合并
```

------

### 3. **`git rebase`**

- **作用**：将当前分支的提交“变基”到另一个分支（通常是远程分支）的顶部，形成线性的提交历史。
- **特点**：
  - 不会像 `merge` 那样生成额外的合并提交（merge commit），保持提交历史的整洁。
  - 会修改本地提交的哈希值（重写提交历史）。
  - 适合在本地分支整理提交记录后再推送到远程。
- **使用场景**：
  - 本地分支基于过时的远程分支时，用 `rebase` 更新到最新。
  - 避免不必要的合并提交，保持提交历史线性。

**示例**：

```shell
git fetch origin         # 先获取远程更新
git rebase origin/main   # 将当前分支变基到 origin/main
```

------

### 关键区别总结：

| 命令         | 作用                                                         | 是否修改本地历史 | 适用场景                                 |
| :----------- | :----------------------------------------------------------- | :--------------- | :--------------------------------------- |
| `git fetch`  | 仅下载远程更新，不自动合并。                                 | 否               | 查看远程变更，再决定是否合并，暂不合并。 |
| `git pull`   | 下载远程更新并自动合并（默认 `merge`，可配置为 `rebase`）。  | 是               | 快速同步远程变更并合并。                 |
| `git rebase` | 将本地提交移动到远程分支的顶部，形成线性历史（需先 `fetch`）。 | 是               | 整理提交历史，避免合并提交。             |

------

### 工作流示例：

1. **安全更新**（推荐）：

   ```shell
   git fetch origin        # 查看远程更新
   git diff origin/main    # 比较本地和远程的差异
   git rebase origin/main  # 变基到远程分支（或 git merge）
   ```

2. **快速更新**（直接合并）：

   ```shell
   git pull origin main    # 等同于 fetch + merge
   ```

3. **保持线性历史**：

   ```shell
   git pull --rebase origin main  # 等同于 fetch + rebase
   ```

------

### 注意事项：

- **`rebase` 会重写历史**：不要在公共分支（如 `main`）上使用 `rebase`，以免影响他人。

- **冲突处理**：`pull`（merge）和 `rebase` 都可能产生冲突，需要手动解决。

- **配置默认行为**：

  ```shell
  git config --global pull.rebase true  # 将 git pull 默认设为 rebase 模式
  ```

## 二. git rebase 和 git merge

`git rebase` 和 `git merge` 都是用于整合不同分支的更改，但它们的**工作方式、提交历史记录和适用场景**有显著区别。以下是详细对比：

------

### 1. 核心区别

| 特性               | `git merge`                                    | `git rebase`                         |
| :----------------- | :--------------------------------------------- | :----------------------------------- |
| **提交历史**       | 保留原始分支结构，生成合并提交（Merge Commit） | 线性历史，不生成合并提交             |
| **操作方式**       | 将目标分支合并到当前分支                       | 将当前分支的提交“移动”到目标分支顶部 |
| **历史记录清晰度** | 可能有交叉的分支历史（图形化复杂）             | 提交历史呈一条直线（更简洁）         |
| **适用场景**       | 公共分支（如 `main`）、团队协作                | 本地分支整理、个人开发分支           |
| **是否重写历史**   | 否（安全）                                     | 是（谨慎在公共分支使用）             |

### 2. 图示对比

**初始状态（两个分支）：**

```tex
      A---B---C  (feature)
     /
D---E---F---G    (main)
```

**使用 `git merge main` 后：**

```tex
      A---B---C---H  (feature)
     /         /
D---E---F---G        (main)
```

- **新增合并提交 `H`**，保留了分支的拓扑结构。

**使用 `git rebase main` 后：**

```tex
              A'---B'---C'  (feature)
             /
D---E---F---G                (main)
```

- **`feature` 的提交（A/B/C）被复制到 `main` 的顶部**（哈希值改变），历史呈线性。

------

### 3. 关键差异详解

**（1）提交历史的处理**

- `merge`：
  - 保留所有原始提交，生成一个新的合并提交（`H`）。
  - 适合需要保留分支协作历史的场景（如团队开发的公共分支）。
- `rebase`：
  - 将当前分支的提交“重新播放”到目标分支的最新提交上，**重写提交历史**。
  - 适合整理本地分支的提交记录（如清理 `WIP` 提交）。

**（2）冲突处理**

- **`merge`**：
  - 冲突只需解决一次（在合并提交 `H` 时）。
- **`rebase`**：
  - 可能需要**多次解决冲突**（因为每个提交会逐个重新应用到目标分支）。

**（3）安全性**

- **`merge`**：
  - 安全，不会修改已有提交的历史。
- **`rebase`**：
  - **重写历史**，如果已推送到远程仓库，强制推送（`git push --force`）可能影响他人。

------

### 4. 何时用 `merge`？何时用 `rebase`？

使用 `merge` 的场景：

- 合并公共分支（如 `main` 或 `develop`）。
- 需要保留分支的完整历史（如团队协作的可追溯性）。

使用 `rebase` 的场景：

- 整理本地分支的提交（如压缩多个 `fix` 提交）。
- 在推送前将本地分支更新到远程最新状态（避免多余的合并提交）。
- **仅限尚未推送的分支**（避免历史冲突）。

------

### 5. 命令示例

**（1）合并分支（`merge`）**

```shell
git checkout feature
git merge main      # 将 main 合并到 feature，生成合并提交
```

**（2）变基分支（`rebase`）**

```shell
git checkout feature
git rebase main    # 将 feature 的提交移动到 main 的顶部
```

**（3）`git pull` 时默认使用 rebase（可选配置）**

```shell
git config --global pull.rebase true  # 将 pull 设为 rebase 模式
```

------

### 6. 黄金法则

> **不要对已推送到远程仓库的公共分支使用 `rebase`**
> （除非你清楚后果并和团队达成一致）。

------

### 总结

| **需求**                  | **用 `merge`** | **用 `rebase`** |
| :------------------------ | :------------- | :-------------- |
| 保留完整分支历史          | ✅              | ❌               |
| 整理本地提交记录          | ❌              | ✅               |
| 合并公共分支（如 `main`） | ✅              | ❌（危险）       |
| 保持提交历史线性          | ❌              | ✅               |
